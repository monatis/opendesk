Tools Reference#

These are the tools the opendesk-mcp server (and opendesk mcp) exposes over MCP. They are defined in opendesk-rs/src/mcp/server.rs (list_tools). There is no in-process tool API to import: agents call the tools over MCP, and Rust programs can use the opendesk-rs crate directly (see Programmatic Use).

Tool priority rule: ui first; screenshot + mouse for surfaces with no accessible elements.

Tool

Description

ui

Accessibility-based UI interaction: list elements, click by name, type, read values

screenshot

Screen capture (PNG or JPEG), optional region / zoom

Pixel-level mouse control using screenshot coordinates

Type text, press keys and chords, hold keys, timed sequences

app

Open, close, focus, and list applications

clipboard

Read and write clipboard text

opendesk_exec

Run a shell command on the target machine (see below)

Show this machine’s server-side audit log

learn

Save and replay written procedures

schedule

Store named schedules (see Scheduler)

Not available in the Rust version

Admin tools (opendesk_peers, opendesk_use, opendesk_status, opendesk_discover, opendesk_describe, opendesk_capabilities, opendesk_disconnect, opendesk_guard, opendesk_privacy, opendesk_view) are described in Remote: MCP Integration.

Routing: the peer argument#

screenshot, mouse, keyboard, app, ui, clipboard and opendesk_exec accept an optional peer string. Without it, the call goes to the session’s default peer (opendesk_use, then the persistent default from opendesk peers default, then local). audit, learn and schedule always run on the machine hosting the MCP server.

Input guard#

mouse and keyboard accept an optional guard object:

{ "action": "type", "text": "hello", "guard": { "process": "notepad" } }

title is a case-insensitive substring of the foreground window title; process is the executable name (with or without .exe). The check runs on the machine receiving the input, right before it is sent. If the foreground window does not match, the call fails with input refused: ... and nothing is typed or clicked. opendesk_guard (action: set / clear / show, plus title / process) sets a session default that applies to every mouse and keyboard call, local or remote; a per-call guard overrides it.

Foreground-window detection is implemented for Windows only. On other platforms the foreground window cannot be determined, so any non-empty guard refuses input.

Where to run it

The result reports the exit code, stdout and stderr. On timeout the whole process tree is killed (a Job Object on Windows, a process group on Unix), and the output collected so far is returned with the status TIMED OUT (process tree killed; output below is partial).

The CLI equivalent is opendesk exec COMMAND [--peer NAME] [--shell SH] [--timeout S], or opendesk exec --file script.ps1 ... to send the contents of a local script file instead (this sidesteps quoting in the local shell). The CLI exits with the command’s exit code, or 124 on timeout.

Waiting for the UI: opendesk_wait and opendesk_events#

Instead of sleeping a fixed time after an action, wait for its effect.

opendesk_wait blocks until an element reaches a state, then returns the element and how long it took; it fails after timeout_secs (default 10, max 120). States: attached, detached, visible, hidden, enabled, disabled, focused, unfocused.

{ "selector": "button[name=\"OK\"]", "state": "detached", "app": "notepad", "timeout_secs": 5 }

opendesk_events keeps an event log for one app (default: the foreground app): focus moves, value/name/state changes, structure changes, windows and menus opening or closing, and live-region announcements.

  • {"action": "start", "app": "chrome"} begins watching (restarting any watch).

  • {"action": "read", "wait_ms": 2000} returns the events since the last read, waiting up to wait_ms for the first one, so “act, then read” sees the reaction. The log keeps the latest 2000 events and reports how many were dropped.

  • {"action": "stop"} ends the watch. A peer also stops it when the controller’s session ends.

Both route to a remote peer like the other tools (peer), as long as that peer’s opendesk advertises the ui.wait / events capabilities.

Peer environment: opendesk_capabilities#

Shows the capabilities a peer advertises and its environment: OS version, locale, keyboard layout of the foreground window, time zone, the clock offset from this machine, and each display’s position, size and scaling. Check it before typing or clicking on an unfamiliar peer.

File transfer: opendesk_file#

Copies files between this machine and a remote peer, verified by SHA-256.

  • {"action": "push", "local_path": "C:/build/app.exe", "remote_path": "~/bin/app.exe"}

  • {"action": "pull", "remote_path": "~/logs/run.log", "local_path": "./run.log"}

  • {"action": "stat", "remote_path": "~/bin/app.exe"} reports size and SHA-256.

Data moves in 1 MiB chunks into <destination>.opendesk-part; the destination is replaced only after the whole file’s checksum matches, so an interrupted or corrupted copy never leaves a half-written file. ~ in remote_path is the peer’s home directory. Replacing a file another program has open (for example a running .exe on Windows) fails with a clear error.

From the command line:

opendesk push ./app.exe "~/bin/app.exe" --peer old-pc
opendesk pull "~/logs/run.log" ./run.log --peer old-pc

Background jobs: opendesk_exec with background: true, and opendesk_job#

For anything that may run longer than a few minutes, start it in the background and poll it, instead of holding one long opendesk_exec open:

{ "command": "C:/lab/run-batch.ps1", "background": true, "peer": "old-pc" }

returns a job id at once. Then opendesk_job:

  • {"action": "poll", "job_id": 3, "wait_ms": 5000} returns the output produced since the previous poll and the status (running, exit code, timed out, killed). With wait_ms it waits until there is new output or the job ends. A finished job is forgotten once its final output has been returned.

  • {"action": "kill", "job_id": 3} kills the job’s whole process tree.

  • {"action": "list"} shows known jobs.

Background jobs have no time limit unless timeout_secs is given, and they keep running if the controller disconnects. Up to 16 can run at once per machine.
